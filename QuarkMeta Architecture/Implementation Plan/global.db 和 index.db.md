**是的，确实采用了两个独立的数据库文件：`global.db` 和 `index.db`。**

之所以要坚决把它们在物理上拆开，而不是混在同一个数据库里，核心原因有三个：

---

### 1. 数据性质完全不同（真理 vs 缓存）
* **`global.db`（配置真理库）**：
  * 存放的是应用全局真实数据：收藏夹、历史访问记录、驱动器卷离线信息、全局标签词典。
  * **绝对不能随便删除**，一旦删掉，用户的收藏和使用习惯全部丢失。
* **`index.db`（纯派生索引缓存）**：
  * 存放的是从各个文件夹 `.QuarkMeta.json` 抽取出来的搜索索引。
  * **随时可以删掉重建**。即使文件损坏、版本升级或用户手动清空，只要后台重新扫一遍 JSON 就能 100% 还原。

---

### 2. 彻底断绝 UI 卡顿（锁与连接的物理隔离）
这是最致命的原因：
* 现在的 `global.db` 在代码里绑定了一把全局大互斥锁（`DatabaseManager::getGlobalMutex()`）。UI 线程在渲染标签、下拉菜单、读取驱动器时，都要去抢这把锁。
* 如果把跨文件夹成千上万条的 JSON 元数据同步也往 `global.db` 里面塞，哪怕底层 SQLite 开了 WAL 模式，**后台批量写入也会长时间霸占应用层全局锁，直接导致 UI 线程在读标签时假死排队**（这也是之前 Claude 在审查时确认的第一大卡顿隐患）。
* 拆成 `index.db` 后，后台同步拥有自己专用的写连接和文件，**跟 `global.db` 的全局锁没有任何物理瓜葛，前台读 UI 完全无感**。

---

### 3. 容错与灾备隔离
* 后台同步由于涉及大量并发、大批量写入，遇到系统突然断电或强退时，索引损坏的概率远高于低频读写的配置库。
* 独立为 `index.db` 后，即便这个索引库写坏、锁死、事务崩溃，程序启动时**直接 `QFile::remove("index.db")` 删库重建即可**，不会波及用户的任何核心配置和收藏数据。
